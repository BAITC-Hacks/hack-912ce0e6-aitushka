# Дополнительная аналитика: проект решения

Статус: рекомендуемый вариант реализован 23 сентября 2026. Ниже сохранено обоснование проекта; фактические правила, API и демонстрация описаны в `METHODOLOGY.md`, `architecture.md` и `DEMO.md`.

Результат реализации: общий индекс исходных операций, шесть типов событий, ограниченный поиск маршрутов A→B→C и циклов длины 2–4 с проверкой дат, карточка и граф события, справка HTML/JSON. Обязательные формулы ролей и приоритета сохранены. Fingerprint передаётся на уровне ответа и проверяется при детализации, графе и скачивании; связи `related_pattern_ids` отложены. Для циклов используется ограниченный обход в глубину, а не полный перебор `simple_cycles`. Справка в PDF доступна через печать HTML; отдельного серверного PDF нет. Исследовательские варианты раздела 8, более длинные маршруты и оценка статистической необычности остаются дальнейшими расширениями.

## 1. Рекомендуемый подход

Добавить единый слой аналитических событий для временных паттернов, повторяющихся маршрутов и направленных циклов. Карточка клиента, граф и скачиваемая справка используют одни и те же события и доказательства. Первая версия детерминированная, работает локально, без обязательного LLM.

Разделять:

- **Наблюдаемый факт:** перечисленные переводы действительно присутствуют в выгрузке.
- **Выполненное правило:** значения прошли опубликованные пороги детектора.
- **Интерпретацию:** возможное объяснение структуры, которое нужно проверить.

Число совпадений и сила правила не являются вероятностью нарушения. Новые события сначала добавляются к текущим ролям и приоритету как отдельные основания для исследования. Изменение рейтинга — отдельный эксперимент с аудитом результатов.

## 2. Что позволяют реальные данные

Выгрузка включает только даты, без времени суток и идентификаторов операций; период — июль 2026. Наблюдаются внутрибанковские переводы от 5 000 KZT и обход от seed по исходящим связям до четырёх переходов.

Разведочные подсчёты по исходным Parquet:

| Наблюдение | Результат |
|---|---:|
| Клиенты с входящими только в один день | 1 578 |
| Клиенты с входящими минимум в пять дней | 141 |
| Клиенты с исходящими минимум в пять дней | 194 |
| Пары «получатель–день» с минимум тремя плательщиками | 66, у 38 получателей |
| Повтор минимум трёх общих плательщиков на двух датах | 5 пар дат, у 3 получателей |
| Направленные маршруты A→B→C, три разных клиента | 11 871 |
| Такие маршруты с последовательными датами, задержка 1–2 дня | 2 071 |
| Такие маршруты с минимум двумя непересекающимися дневными эпизодами внутри маршрута | 86 |
| Структурные циклы длины 2 / 3 / 4 | 177 / 41 / 169 |
| Из них с хотя бы одним строго последовательным эпизодом, 1–2 дня на шаг | 90 / 7 / 1 |

Это исследование осуществимости, не результаты финального детектора и не оценка его точности. Для маршрута даты первого ребра перебирались по порядку; каждой назначалась самая ранняя ещё не использованная подходящая дата второго ребра. Между разными маршрутами операции могут пересекаться. Циклы объединены по вращению последовательности, но обратное направление не объединяется; проверены все возможные начальные вершины.

Найдены 97 избыточных относительно первого в группе полностью совпадающих строк транзакций. Без transaction_id нельзя считать их ошибочными дубликатами и удалять: это могут быть разные операции.

## 3. Общая подготовка и происхождение доказательств

1. Использовать существующую валидацию сумм, направлений и схемы входа.
2. Сохранить все строки операций. Для ссылок назначить технический идентификатор внутри версии набора; одинаковые строки сохранять отдельными экземплярами. Это идентификатор строки выгрузки, не банковский ID.
3. Построить дневные агрегаты для каждого клиента и направления: сумма, число операций, множество контрагентов. Отдельно индексировать дневные рёбра `(src, dst, date)`.
4. Пустой день означает отсутствие переводов в этой выборке. Самопереводы не считать транзитом, групповыми поступлениями или многоузловым циклом.
5. Каждый результат привязывать к fingerprint входа, версии алгоритма и параметрам. Все gid в JSON остаются строками.

## 4. Временные события

### 4.1. Всплеск относительно собственной истории

Проверять вход и выход отдельно. Для дня d базу составляют другие активные дни клиента в выбранном направлении. Это ретроспективное сравнение внутри месяца; будущие относительно d дни допустимы только в таком режиме, не в онлайн-детекторе.

Стартовые, ещё не откалиброванные параметры:

- минимум пять **других** активных дней для сравнения;
- всплеск числа операций: не менее пяти операций в d и число операций не менее трёх медиан остальных активных дней;
- всплеск суммы: не менее трёх операций в d и сумма не менее трёх медиан остальных активных дней;
- хранить обе причины отдельно, объединять в одну карточку дня.

При нехватке истории результат сравнения — `insufficient_history`, а не «норма». Можно показать описательную концентрацию: доля месячной суммы направления, пришедшаяся на день; она сама по себе не означает необычность.

Не использовать медиану всех календарных дней без обработки редкой активности: у большинства клиентов она будет нулевой. Дополнительный вариант для достаточно длинной истории — медиана и MAD с явно заданной обработкой нулевого MAD. Формула и пороги в любом случае должны оставаться объяснимыми.

### 4.2. Групповые поступления и повторяющийся состав

- Событие: не менее трёх уникальных плательщиков одному получателю в один календарный день.
- Повтор: пересечение составов плательщиков двух разных дат содержит минимум трёх клиентов.
- Хранить общий состав, все участвующие даты и операции. Парные совпадения дат не называть независимыми группами; объединять одинаковое ядро и показывать поддержку по датам.
- Визуально различать разовое поступление и повтор состава. Не вводить жёсткий порог сходства полных групп в первой версии: дополнительные плательщики не должны скрывать повтор ядра.

Формулировка: «В один день поступили переводы от N клиентов; K из них встречаются также на датах …». Нельзя утверждать одновременность или согласованность действий по датам без времени суток.

### 4.3. Связь со следующим выходом

Расширить текущий FIFO журналом распределений: даты и суммы входа, дата выхода, использованная часть суммы. Сумма расходуется один раз внутри расчёта данного узла. Сопоставлять только более ранний вход с выходом через 1–2 календарных дня.

В справке можно связать групповое поступление с последующим совместимым выходом. Сопоставление зависит от принятого FIFO, не устанавливает происхождение денег и не является глобальной трассировкой по всей сети.

## 5. Маршруты и циклы

### 5.1. Два уровня результата

**Структурный кандидат:** нужные направленные рёбра существуют за месяц.

**Эпизод с последовательными датами:** для всех шагов есть операции, даты строго возрастают, каждый следующий шаг происходит через 1–2 дня. Упорядоченные даты доказывают последовательность операций, но не движение одной суммы.

Если несколько шагов имеют одну дату, это отдельное состояние `same_day_order_unknown`. Если порядок дат обратный, строгого эпизода нет. Отсутствие подходящего эпизода при текущем окне не означает отсутствия переводов по этому маршруту вообще.

### 5.2. Повторяющиеся маршруты

Первая версия: A→B→C, три разных клиента, минимум два эпизода на разных датах старта. Каждое дневное ребро используется максимум один раз при подсчёте поддержки **этого маршрута**. Не увеличивать число повторов перебором всех комбинаций одних и тех же операций.

Показывать участников, даты, количество повторов, операции и суммы каждого шага. Сумму всех рёбер нельзя называть объёмом прошедших по маршруту средств. В первой версии итоговый «объём маршрута» не нужен. Маршруты могут разделять операции, поэтому их суммы и поддержки не складывать как независимые потоки.

Расширение до трёх рёбер выполняется после аудита двухшаговых маршрутов. Для расчёта совместимого объёма понадобится явное распределение денежных ёмкостей по времени с фиксацией области расчёта и правил использования средств.

### 5.3. Направленные циклы

- Искать простые циклы от двух до четырёх рёбер только в сильно связанных компонентах.
- A→B→A и A→B→C→A показывать отдельно по длине; одиночные самопереводы исключить.
- Один структурный цикл хранить один раз независимо от поворота его списка вершин. Противоположное направление — другой цикл.
- Для хронологии проверить все начальные вершины: каноническая вершина хранения не обязательно первая по дате.
- Показывать найденный датированный эпизод, суммы на каждом шаге и повторяемость. Термин «кандидат на возвратный маршрут» предпочтительнее утверждения «деньги вернулись».

Число циклов может быстро расти. Ограничить длину и число рассматриваемых кандидатов, использовать стабильный порядок обхода. При достижении лимита возвращать `search_complete=false`, область и причину остановки. Лимит вычисления отличать от пагинации показа готовых событий.

Применим `networkx.simple_cycles(..., length_bound=4)`; функция поддерживает ограничение длины и обработку сильно связанных компонент: https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.cycles.simple_cycles.html.

## 6. Справка аналитика

Справка собирается шаблонами из того же результата, что карточка. Структура:

1. gid, период, роль, альтернативная роль, приоритет и числовые основания;
2. входящие/исходящие суммы, число переводов и контрагентов;
3. временные события и маршруты со ссылками на доказательства;
4. ограничения, относящиеся к этому клиенту;
5. следующий запрос данных и вопрос, который он поможет проверить;
6. версия данных, конфигурации и алгоритма.

Примеры условных рекомендаций:

| Основание | Предложение аналитику |
|---|---|
| Граница глубины | Запросить продолжение исходящих переводов за пределами четвёртого колена |
| Seed / неизвестный вход | Запросить полные входящие операции и начальный остаток за рассматриваемый период |
| Шаги маршрута в один день | Запросить точное время операций, чтобы проверить порядок |
| Событие у края месяца | Расширить период наблюдения на соседние дни |
| Близкие оценки ролей | Рассмотреть обе гипотезы и недостающие данные для их различения |

Тексты формулируют предложения, приложение не отправляет запросы автоматически. Не добавлять ФИО, вид деятельности, отношения между людьми и другие отсутствующие атрибуты. Если детектор не завершён, это явно отражается в справке; «не найдено» не подменяет «не проверено».

Формат первой версии: HTML для чтения, скачивания и печати в PDF; JSON для проверки. В дальнейшем возможен серверный PDF. Не передавать большой gid как число JavaScript.

## 7. Интеграция

Предлагаемые модули Python:

- `event_data.py`: общие дневные агрегаты, индексы и происхождение операций;
- `temporal_patterns.py`: всплески и группы, журнал существующего FIFO;
- `route_patterns.py`: направленные маршруты, циклы, проверка дат;
- `analyst_report.py`: шаблонная справка из измерений и событий.

Добавить к `AnalysisResult` события и метаданные покрытия поиска. Новые вычисления выполняются в пайплайне и кешируются вместе с результатом. API и CLI используют их совместно; обязательные CSV сохраняют действующие поля и смысл.

Минимальный контракт события: `pattern_id`, `kind`, `gids`, `date_from`, `date_to`, `measurements`, `rule`, `evidence_refs`, `limitations`, `related_pattern_ids`, `fingerprint`. Состояние поиска хранится отдельно: найдено / не найдено в проверенной области / недостаточно данных / поиск ограничен.

Предлагаемые endpoints:

- `GET /api/clients/{gid}/patterns` — события клиента;
- `GET /api/patterns/{pattern_id}` — операции и доказательства;
- `GET /api/clients/{gid}/report?format=html|json` — справка;
- расширение `/api/graph` параметром выбранного события.

При переходе от события к графу передаётся версия результата; при смене данных UI обновляет событие и связанные экраны вместе. Все узлы и рёбра выбранного маршрута сохраняются в отображаемом графе, даже если обычный лимит окружения исключил бы их. Подсвеченные суммы относятся к выбранным датам; месячные суммы обозначаются отдельно.

В Next.js добавить блок «События» в карточку, фильтр «Есть паттерны», переход «Показать на графе» и кнопку «Скачать справку». Не требуется отдельный пункт навигации для каждого детектора. Несколько правил на одном дне объединять для чтения, сохраняя отдельные основания.

## 8. Варианты реализации

| Вариант | Состав | Компромисс |
|---|---|---|
| Минимальный | Поступления от нескольких плательщиков, пики с достаточной историей, структурные циклы, шаблонная справка | Быстрее; связи между событиями и временная проверка маршрутов ограничены |
| Рекомендуемый | Общий слой доказательств, временные детекторы, повторяющиеся двухшаговые маршруты, циклы до четырёх рёбер с проверкой дат, подсветка и справка | Больше работы по интеграции и тестам; наиболее содержательный результат для защиты |
| Исследовательский | Статистическая необычность при выбранной нулевой модели, более длинные маршруты, распределение потоков, необязательный LLM для перефразирования справки | Требует отдельной валидации, контроля множественных проверок, производительности и дополнительных ограничений |

У LLM нет роли источника сумм, маршрутов или выводов. Если он добавляется, он получает только проверенный пакет доказательств, а локальная шаблонная справка остаётся доступной.

## 9. Проверка и порядок разработки

1. Ввести контракт событий и дневной индекс. Зафиксировать исходные роли, рейтинг и CSV для сравнения.
2. Реализовать временные события и ссылки на операции. Проверить чувствительность порогов: множитель 2/3/4; три/четыре/пять плательщиков.
3. Реализовать маршруты и циклы: обратный порядок дат, один день, повтор без повторного использования дневного ребра, повороты циклов, пересечения разных маршрутов.
4. Подключить карточку и граф; из доказательств собрать справку. Проверить совпадение цифр на экране и в экспорте.
5. Разобрать примеры вручную, повторить полный расчёт, измерить время, обновить методологию и демо.

Обязательные сценарии: пустые вход/выход; изолят; одна операция; устойчивый поток; всплеск; повторяющаяся и меняющаяся группа; seed; граница глубины и месяца; одинаковые строки; большие gid; нулевой MAD при расширенном сравнении; лимит поиска. Проверять воспроизводимость аналитических измерений и результатов при перестановке строк входа, сохранение сумм и отсутствие скрытого двойного зачёта.

Без размеченных ролей и событий нельзя обещать accuracy/F1. Отдельно оцениваются корректность на известных синтетических сценариях, объяснимость реальных примеров, число сигналов и устойчивость к параметрам. Полный локальный пересчёт должен оставаться в пределах пяти минут по ТЗ.

Справка по MAD, если выбран расширенный вариант: https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.median_abs_deviation.html.
