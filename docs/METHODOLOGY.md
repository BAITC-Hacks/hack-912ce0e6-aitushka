# Методика: роли, сообщества и приоритет проверки

Результат — воспроизводимые структурные гипотезы для аналитика. Размеченных ролей нет; `role_score` и `priority_score` не являются вероятностями нарушения. Пороги — предварительная эвристика, зафиксированная в `config.json`. Отсутствие выраженной роли не означает низкий риск за пределами выборки.

## Общие определения

`in_deg` / `out_deg` — число разных плательщиков / получателей. `in_kzt` / `out_kzt` — суммы наблюдаемых переводов за период. `r = pass_through = out_kzt / in_kzt`; при нулевом входе `r` не определено. `seed_reach` — количество разных исходных seed, от которых узел достижим по направленным путям; собственный seed не учитывается. Достижимость не доказывает прохождение одних и тех же денег.

`seed_reach` считается по всем направленным путям объединённого графа, без ограничения длины четырьмя переходами. Поле `depth` хранит минимальную глубину обнаружения от любого seed; объединение найденных рёбер может создавать пути длиннее четырёх переходов от другого seed. Разные достижимые seed могут сходиться задолго до текущего узла и далее иметь общий маршрут. Поэтому число seed не равно числу независимых каналов поступления или прямых плательщиков.

`betweenness` — нормированное посредничество в ориентированном графе по числу переходов, без использования суммы в качестве длины. `intercluster_degree` — количество **разных чужих сообществ**, с которыми у узла есть входящие или исходящие связи; своё сообщество не считается. Узел на максимальной глубине (`depth >= max_depth`) имеет ограниченное наблюдение исходящих.

Для всех неотрицательных признаков используется `N(x) = min(x / Qq(x > 0), 1)`, где по умолчанию `q=0.95`, квантиль считается по положительным значениям соответствующего столбца с линейной интерполяцией. Нули сохраняются нулями. Если положительных значений нет, весь нормированный признак равен нулю. Параметр `normalization_quantile` применяется и к ролям, и к приоритету. Масштабы приоритета сохраняются в metadata расчёта, масштабы ролей доступны в `DataFrame.attrs['role_parameters']`.

## Сообщества

Louvain работает с неориентированной проекцией: `weight(A,B) = sum_kzt(A→B) + sum_kzt(B→A)`. Встречные рёбра складываются, а не перезаписываются. Нулевые веса не участвуют в поиске сообществ. Исходный ориентированный граф сохраняется. Узлы без положительных связей получают отдельные сообщества. Самоперевод, если он есть в данных, остаётся петлёй и входит во внутренний оборот один раз.

Входные узлы и рёбра сортируются по `gid`; фиксированы `random_seed=42`, `community_resolution=1` и версии зависимостей. Сообщества нумеруются с нуля в порядке минимального `gid`. Обнаруженное количество сообществ не задаётся заранее. Изменение данных или параметров может изменить состав и идентификаторы групп.

`clusters.csv` содержит размер, количество seed и сумму исходных направленных рёбер с обоими концами внутри сообщества. Межкластерные рёбра в эту сумму не входят. `top_gids` — до пяти узлов по `priority_score` с сортировкой по `gid` при равенстве, разделитель `;`. Гипотеза строится из размера, суммы и счётчиков ролей; принадлежность к сообществу сама по себе не доказывает общую организацию.

## Допустимость и сила ролей

Недопустимая роль получает оценку 0. Значения оценок не округляются до выбора роли. Основная роль — максимум. При точном равенстве порядок: `coordinator`, `consolidator`, `distributor`, `transit`, `terminal`, `peripheral`. Порядок можно изменить ключом `role_tie_order` верхнего уровня, содержащим все шесть ролей. В `alternative_role` записывается вторая допустимая содержательная роль, `none`, если её нет. `alternative_role_score` показывает её силу. Все шесть оценок доступны в столбцах `score_<role>`.

Обозначим `S = seed_reach`, `B = betweenness`, `C = intercluster_degree`, `T = clip(temporal_share, 0, 1)`, `F = out_deg / max(in_deg, 1)`.

| Роль | Условие допуска | Формула силы |
|---|---|---|
| `consolidator` | `in_deg >= 3` и `S >= 2` | `0.50 + 0.20*N(in_deg) + 0.15*N(S) + 0.15*R` |
| `distributor` | `out_deg >= 10` и `F >= 2` | `0.50 + 0.30*N(out_deg) + 0.20*min(F/(2*distributor_fan_ratio),1)` |
| `transit` | Не seed, не граница; положительные вход/выход и `0.8 <= r <= 1.2` | `0.55 + 0.30*L + 0.15*T` |
| `terminal` | Не seed, не граница; положительный вход, `out_deg=0` | `0.55 + 0.25*N(in_kzt) + 0.20*N(in_deg)` |
| `coordinator` | `B>0`, `B>=Q90(B>0)`, `S>=2`, `C>=2` | `0.55 + 0.25*N(B) + 0.10*N(S) + 0.10*min(C/(2*coordinator_min_communities),1)` |
| `peripheral` | Всегда допустима как резервная роль | `0.05` для изолята, иначе `0.10` |

Все результаты ограничены диапазоном `[0,1]`. Пороги таблицы — значения по умолчанию. Читаемые из `roles` параметры: `consolidator_min_in`, `consolidator_min_seed` (при отсутствии 2), `distributor_min_out`, `distributor_fan_ratio`, `transit_min_ratio`, `transit_max_ratio`, `coordinator_quantile`, `coordinator_min_seed`, `coordinator_min_communities`. Для квантиля посредничества используются только положительные значения; если их нет, координаторов нет.

`R = clip(1-r,0,1)` применяется только к узлам с положительным входом, которые не являются seed и не находятся на границе. В иных случаях `R=0` означает отсутствие усиливающего свидетельства удержания. Нельзя читать это как наблюдаемую нулевую долю удержания. У граничного консолидатора роль основана исключительно на схождении входов.

`L = clip(1 - abs(r-1)/max(1-transit_min_ratio, transit_max_ratio-1), 0, 1)` измеряет близость месячных потоков. Интервал должен содержать 1 и иметь ненулевую ширину. `T` усиливает только уже допустимую транзитную гипотезу. Месячное равенство сумм и временное совпадение не доказывают движение конкретных денег. В данных есть дата, но нет времени внутри дня; порядок переводов одного дня неизвестен.

Временной признак рассчитывается FIFO по дневным суммам отдельно для каждого узла. Исходящие сопоставляются только с остатками входящих **предыдущих** календарных дней в окне `temporal_window_days=2`, то есть за 1–2 дня до выхода. Каждая часть входящей и исходящей суммы учитывается не более одного раза. Вход текущего дня добавляется в очередь после сопоставления выхода; самопереводы исключаются. `temporal_share = temporal_matched_kzt / min(наблюдаемый вход, наблюдаемый выход)` по переводам другим клиентам; если знаменатель 0, доля 0. Однодневные совпадения сохраняются отдельно в `same_day_flow_days` без утверждения порядка. Эти правила исключают повторный зачёт суммы и обратное направление времени, но не восстанавливают остатки на счёте и не устанавливают происхождение денег.

`terminal` означает кандидата в конечные получатели в рамках наблюдаемого периода и банка. Отсутствие дальнейших рёбер на последней глубине не допускает эту роль. Seed и граница также исключены из простого правила транзита независимо от отношения сумм. Узлы с исходящими больше входящих сохраняются; карточка сообщает о неполноте входа/периода. Сообщения `evidence` содержат измеренные числа и ограничены 200 символами; полное ограничение доступно в `observation_note`.

## Приоритет проверки

```
priority_score = 0.35*N(seed_reach)
               + 0.25*N(max(in_kzt, out_kzt))
               + 0.25*N(betweenness)
               + 0.15*N(in_deg)
```

Веса читаются из `priority_weights` по ключам `seed_convergence`, `observed_flow`, `brokerage`, `fan_in`; они должны быть конечными, неотрицательными и в сумме давать 1. Неверная конфигурация останавливает расчёт, а не изменяется молча. Параметр `top_n` должен быть не меньше 20. Для учебного графа меньшего размера возвращаются все узлы, для предоставленного набора — выбранные `top_n`.

В таблице сохраняются `norm_<компонент>` и `contribution_<компонент>`. `why` показывает два главных вклада и исходные значения; они являются вкладами в **шкалу приоритета**, не долями суммы денег. Итог сортируется по убыванию значения, затем по возрастанию `gid`. Внутренний идентификатор клиента остаётся int64.

Веса отражают выбранную задачу поиска схождения цепочек и посредников. `role_score` не множитель приоритета. Для seed, изолятов и граничных узлов нет скрытых штрафов или бонусов. Структурные ограничения показываются рядом с результатом. Крупный распределитель с низким числом плательщиков может уступать узлу схождения; интерфейс поэтому также позволяет исследовать роли и суммы напрямую.

## События: единица анализа и доказательная база

События рассчитываются после ролей и приоритета, на той же полной выборке. Детекторы не добавляют баллы рейтингу и не переопределяют роль. Временная доля `T` в уже существующей формуле `transit` сохраняется; новый журнал лишь раскрывает её основание. `pattern_count` считает события с участием клиента, в том числе события других клиентов, где он плательщик или получатель. Поэтому сумма счётчиков по клиентам не равна числу уникальных событий.

Общий индекс хранит исходные операции, дневные направленные рёбра `(src, dst, date)` и дневные входы/выходы клиента. Самопереводы сохраняются в исходных строках, но исключаются из детекторов. Строки с одинаковыми реквизитами не удаляются: каждая остаётся отдельным наблюдением. Ссылка `tx_…_номер` идентифицирует вхождение строки в этой выгрузке, а не банковский ID транзакции. Каноническая сортировка сохраняет ссылки при перестановке входных строк. Во внешнем JSON все `gid` передаются строками, чтобы не потерять точность длинных идентификаторов в браузере.

Каждое событие содержит тип, основной клиент `focus_gid`, всех участников `gids`, даты, измерения, условия правила, ссылки на строки, поддерживающие связи и ограничения вывода. `pattern_id` детерминированно зависит от содержимого события. `input_fingerprint` дополнительно связывает расчёт с файлами, конфигурацией и Python-кодом; при изменении версии открытое событие необходимо обновить.

Основной клиент события и открытый клиент могут различаться. Например, плательщик видит групповое поступление своего получателя. Интерфейс называет основного клиента отдельно. Кнопка «Показать на графе» сохраняет всех участников события, выделяет поддерживающие связи и показывает суммы исходных операций этого события отдельно от месячных сумм. Для FIFO это суммы дневных пулов, не приписанный конкретной связи «прослеженный» объём.

## Временные паттерны

Пороговые значения ниже задаются в `config.patterns`. Это объяснимые эвристики, а не обученные границы аномального поведения.

### Всплески активности

Вход и выход анализируются независимо. Для дня `d` берутся **остальные активные дни** клиента в том же направлении. Если их меньше `burst_min_other_days=5`, всплеск не оценивается; статус сообщает о недостаточной истории. Следовательно, для оценки требуется минимум шесть активных дней вместе с проверяемым. Медиана по всем календарным дням не используется: на редкой истории она часто равна нулю.

Обозначим `m_count` и `m_amount` — медианы числа операций и суммы в остальных активных днях. Событие `burst` создаётся при выполнении хотя бы одного условия:

- Число операций дня не меньше `burst_min_count=5` и не меньше `burst_multiplier=3` медиан `m_count`.
- Число операций дня не меньше `burst_amount_min_count=3`, а сумма не меньше трёх медиан `m_amount`.

Отношение к нулевой медиане не вычисляется. Сработавшие условия объединяются в одно событие дня и направления. Сравнение ретроспективное: остальные дни могут находиться как до, так и после проверяемой даты. Это не прогноз и не оценка сезонности.

В основании доступны показатели пикового дня, значения медиан, отношения к ним, список сравнительных дней и их исходные операции. Основные ссылки события относятся к пиковому дню; сравнительные строки выдаются отдельно, чтобы фон не превращался в выделенный маршрут на графе. Единичный крупный платёж сам по себе не удовлетворяет указанному правилу всплеска. Зарплаты и обычные пакетные расчёты могут удовлетворять ему.

### Групповые поступления и повтор состава

`group_receipts` — дневное поступление от минимум `group_min_payers=3` **разных** плательщиков. Десять переводов одного плательщика не считаются десятью участниками. Известна только общая дата: слово «одновременно» к таким данным не применяется.

`repeated_group` — общий состав минимум из трёх плательщиков, переводивших одному получателю минимум в `group_min_repeats=2` разные даты. Пересечения дневных составов находят общий состав и при наличии дополнительных разных плательщиков. Даты одного общего состава объединяются; для одинакового набора дат сохраняется полный найденный общий состав. Разные пересекающиеся группы могут давать отдельные события.

В доказательную базу повтора входят только операции общих плательщиков на поддерживающих датах. Остальные поступления этих дней не приписываются группе. Перебор общих составов ограничен `max_group_cores=1000` на клиента. При достижении лимита в статусе устанавливается `repeated_group_search_complete=false`, а в выводе явно указана неполнота. Уже найденные составы всё равно проверяются на всех кандидатных датах. Повтор состава не доказывает согласованность действий; возможны регулярные законные платежи.

### Журнал входа и последующего выхода

`transit_window` раскрывает описанное выше FIFO-сопоставление: дата входного пула, дата выходного пула, использованная сумма и ссылки на операции обоих дней. Окно — `temporal_window_days=2`, допустимый лаг 1–2 календарных дня. Более ранний вход потребляется первым; каждая часть суммы расходуется не более одного раза в пределах клиента. Вход сегодняшнего дня становится доступен только после обработки сегодняшнего выхода.

Ссылки относятся ко всему дневному пулу, а использованная сумма — к его совместимой части. Алгоритм не выбирает произвольно, какой конкретно плательщик профинансировал какого получателя. Отсутствие сопоставления на краю месяца не исключает вход до начала выгрузки или выход после её окончания. Событие допустимо для seed и граничного клиента как наблюдаемый факт совместимости; оно само по себе не присваивает исключённую для них роль `transit`.

## Повторяющиеся маршруты и циклы

### Повтор маршрута

`repeated_route` ищет маршрут из двух направленных рёбер `A → B → C`, где все три клиента различны. Для каждого ребра рассматриваются дневные агрегаты. Допустимый эпизод требует строгого увеличения даты: перевод `B → C` наблюдается через 1–2 дня после `A → B`. Несколько одинаковых переводов одного ребра в один день остаются одним дневным шагом.

Два отсортированных ряда сопоставляются от ранних дат к поздним. Внутри одного маршрута каждый дневной шаг используется не более одного раза; выбирается максимальное число совместимых пар дней. Событие возникает при минимум `route_min_repeats=2` эпизодах. В нём сохранены сами эпизоды и их исходные строки, а не все операции этих рёбер за месяц. Если временной поиск остановлен по лимиту, найденное число повторов обозначается как нижняя оценка.

Это повторяемость структуры и последовательности дат, а не установление происхождения денег. Суммы двух шагов могут различаться. Они не складываются в «объём маршрута». Разные маршруты также могут использовать общие операции; запрет повторного использования дневного шага действует внутри одного маршрута, не как глобальное распределение денег по всей сети.

### Циклы

`cycle` ищет простые направленные циклы длиной от двух до `cycle_max_length=4` рёбер. Самопетли исключены. Повороты одного цикла считаются один раз, обратное направление — отдельный цикл, если соответствующие рёбра существуют. Поиск ведётся внутри сильно связных компонент. Для временной проверки началом может быть любой участник цикла, независимо от его канонического номера.

| Статус | Что установлено |
|---|---|
| `chronological` | Найден хотя бы один эпизод со строго возрастающими датами и лагом 1–2 дня на каждом шаге |
| `date_order_unknown` | Строгий эпизод не найден, но есть последовательность неубывающих дат с шагами одного дня; внутридневной порядок неизвестен |
| `structural_only` | Замкнутые связи за период есть; временная проверка завершена, совместимого эпизода в заданном окне не найдено |
| `not_evaluated` | Замкнутые связи есть, но временная проверка не завершена из-за лимита |

Для первых двух статусов сохраняется **один опорный эпизод**, а не оценка числа повторений цикла. Его исходные строки ограничивают доказательную базу. Для структурного или непроверенного цикла сохраняются наблюдаемые операции его рёбер за весь период; это явно другая область данных. Даже строгая хронология не доказывает возврат первоначальной суммы. В частности, встречные переводы в одну дату остаются статусом неизвестного порядка даже при совпадающих суммах.

### Ограничения поиска

По умолчанию проверяется до 50 000 кандидатов маршрутов и до 5 000 циклов. Структурный поиск циклов ограничен 100 000 шагов обхода, временные сопоставления маршрутов и циклов — общим бюджетом 100 000 состояний. Порядок обхода детерминирован. Лимиты, число использованных шагов, завершённость и причины остановки доступны в `pattern_coverage` и метаданных. Ограничение общих групп также учитывается в общей завершённости.

`search_complete=true` означает завершение **заданных правил в заданной области**, а не нахождение всех возможных финансовых схем. Более длинные маршруты, циклы длиннее четырёх рёбер и другие временные окна не проверяются. При неполном поиске отсутствие события не читается как исключение соответствующей гипотезы.

## Справка аналитика

Справка формируется локально из результатов расчёта и исходных строк, без вызова LLM или внешнего AI API. В ней есть роль и альтернатива, основания приоритета, месячные вход/выход, до пяти крупнейших плательщиков и получателей, события с участием клиента, ограничения и рекомендации следующего запроса. Рекомендации обусловлены измерениями: продолжить обход на границе, запросить полную входящую сторону и остаток для seed, расширить период при превышении выхода над входом, получить точное время для событий неизвестного внутридневного порядка, сравнить близкие оценки ролей.

JSON-справка содержит полный найденный набор событий, доказательные строки, сравнительную базу всплесков, параметры и покрытие поиска. HTML — краткая читаемая версия: максимум восемь событий и до трёх эпизодов каждого. При сокращении это указано явно. Приоритет показа типов: повтор маршрута, повтор состава, всплеск, последующий выход, цикл, групповое поступление; это порядок изложения, не новый риск-рейтинг. HTML содержит раскрываемые исходные строки выбранных событий и работает после скачивания без сервера.

PDF получается через кнопку «Печать / сохранить в PDF» в скачанном HTML и диалог браузера. Отдельного серверного PDF-генератора нет. Печатная версия содержит краткую справку; раскрываемые таблицы исходных строк скрыты при печати. Для полного аудита нужно сохранять HTML и JSON вместе с данными расчёта. В справке указаны время расчёта, версия правил и fingerprint.

## Проверка и ограничения

Без разметки не заявляются accuracy, F1 или калиброванная уверенность. Проверяются контракт CSV, числовой диапазон, детерминизм, сохранение всех узлов, корректность встречных рёбер и изолятов, запрет terminal/transit на границе и для seed, а также независимость приоритета от уверенности роли. Значения порядка 200 символов предназначены для экспорта; исходные метрики остаются доступны в карточке.

Роли могут пересекаться. Названия и близкие оценки нужно читать вместе с альтернативой и ограничениями наблюдения. Изменение параметров может менять роли, сообщества и рейтинг; пороги фиксированы для демонстрации, а не обучены на размеченной выборке. Следующая содержательная проверка — экспертная оценка примеров и устойчивость к изменению порогов, периода и полноты выгрузки.

Для новых детекторов проверяются редкая история и границы порогов, отдельный учёт одинаковых строк, исключение самопереводов, строгий порядок дат и границы окна, сохранение сумм FIFO, отсутствие повторного использования дневного ребра внутри маршрута, повороты циклов, неизвестный порядок одного дня и явная остановка по лимитам. Перестановка входных строк не должна менять события и ссылки. На полном предоставленном наборе суммы FIFO-журнала сверены с прежним `temporal_features` для каждого клиента; расхождений не обнаружено.

При конфигурации по умолчанию проверенный расчёт 23.09.2026 даёт 974 уникальных события с участием 1 177 клиентов: 133 всплеска, 66 групповых поступлений, 5 повторов состава, 297 событий последующего выхода, 86 повторяющихся маршрутов и 387 циклов. Из циклов 98 имеют строгий эпизод по датам, 37 — неизвестный порядок внутри дня, 252 — только структурное замыкание. Поиск заданной области завершён без достижения лимитов. Эти счётчики описывают результат правил и не измеряют точность выявления нарушений; после изменения входа или параметров их следует пересчитать.
