# «Граф денег» — AItushka

Локальный инструмент для исследования сети банковских переводов: определяет гипотезы о ролях клиентов, выделяет сообщества, рассчитывает приоритет проверки и объясняет результат конкретными числами. Аналитик может найти клиента по `gid`, исследовать направленные связи и выгрузить результаты.

Данные хакатона: 2 248 клиентов, 3 119 направленных связей, 4 840 переводов за июль 2026 года. Сеть собрана от 81 seed-клиента по исходящим переводам на глубину до четырёх переходов, с порогом 5 000 KZT. Исходные таблицы находятся в `data/`.

Описание исходных полей — в [data/README.md](data/README.md). Папка `starter/` сохраняет оригинальную заготовку организаторов; готовое приложение запускается через `run.py` и использует `src/money_graph/`. Данные предоставлены для работы в рамках хакатона.

## Установка и запуск

Для расчёта нужен Python 3.12. Для интерфейса дополнительно нужны Node.js и npm. На рабочей машине используются Python 3.12.14, Node.js 24.16.0 и npm 11.13.0. В PowerShell из корня репозитория:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
npm install --prefix frontend
```

`requirements.txt` фиксирует прямые Python-зависимости и подключает `requirements-lock.txt`. Зависимости Next.js находятся в `frontend/package.json` и `frontend/package-lock.json`.

Одна команда выполняет анализ, сохраняет результаты и запускает интерфейс:

```powershell
.\.venv\Scripts\python.exe run.py --data data --out outputs --ui
```

Откройте [http://localhost:3000](http://localhost:3000) в браузере. Команда сначала рассчитывает CSV, затем запускает Python API на `127.0.0.1:8000`, проверяет его готовность и запускает Next.js на `127.0.0.1:3000`. `Ctrl+C` в этом терминале останавливает оба сервера и их дочерние процессы. При неожиданном завершении одного сервера второй тоже останавливается.

Для расчёта без интерфейса:

```powershell
.\.venv\Scripts\python.exe run.py --data data --out outputs
```

Пользовательскую конфигурацию и порт можно задать явно:

```powershell
.\.venv\Scripts\python.exe run.py --data data --out outputs --config config.json --ui --port 3000 --api-port 8000
```

При занятых портах укажите другие значения `--port` и `--api-port`. Если Node.js/npm не находятся через `PATH`, можно задать `NODE_BINARY` и `NPM_BINARY`; в Windows для `NPM_BINARY` подходит полный путь к `npm-cli.js`. При отсутствии зависимостей интерфейса launcher выдаёт команду `npm install --prefix frontend`.

На Linux/macOS используйте `python3.12 -m venv .venv`, затем `.venv/bin/python` вместо `.\.venv\Scripts\python.exe`. После установки зависимостей для расчёта и просмотра локального графа интернет, API-ключи и платные сервисы не требуются. Первая установка требует доступа к реестрам Python/npm. Телеметрия Next.js отключается launcher через `NEXT_TELEMETRY_DISABLED=1`. Для команды без `--ui` Node.js не требуется.

## Как работать с результатом

1. Откройте обзор и топ клиентов. `priority_score` задаёт порядок проверки в этой выборке.
2. Найдите `gid`, посмотрите роль, числовые признаки и ограничения наблюдения.
3. В блоке «События и маршруты» выберите тип события и раскройте основания: даты, суммы, правило и исходные операции. Фильтр «Есть события и маршруты» оставляет в очереди участников найденных событий.
4. Нажмите «Показать на графе»: будут показаны участники события и суммы его операций. Кнопка «Обычный граф» возвращает исследование окружения за весь период.
5. Скачайте справку клиента: автономный HTML с основаниями, ограничениями и следующими шагами. Его можно распечатать в PDF. Полный пакет событий и операций доступен через `/api/clients/{gid}/report?format=json`.
6. Скачайте обязательные CSV или возьмите файлы из указанной папки результатов.

Метрики рассчитаны на всей предоставленной сети. Фильтры меняют видимый фрагмент, а не исходные показатели клиента. `gid` — идентификатор, его нужно копировать целиком; в браузерном графе он передаётся строкой для сохранения точности больших `int64`.

## Выгрузки

| Файл | Обязательные поля |
|---|---|
| `nodes_roles.csv` | `gid`, `role`, `role_score`, `cluster_id`, `priority_score`, `evidence` |
| `clusters.csv` | `cluster_id`, `n_nodes`, `n_seed`, `sum_kzt_internal`, `top_gids`, `hypothesis` |
| `top_nodes.csv` | `rank`, `gid`, `role`, `priority_score`, `why` |
| `run_metadata.json` | параметры и сведения о выполненном расчёте |

В таблице ролей сохраняется каждый входной клиент, включая изолированные узлы. `role_score` и `priority_score` находятся в диапазоне `[0, 1]`. Объяснение `evidence` содержит не более 200 символов. Топ включает не менее 20 клиентов для предоставленного датасета; при одинаковом приоритете порядок определяется `gid`. Дополнительные диагностические столбцы помогают проверить расчёт.

## Правила и архитектура

Интерфейс в `frontend/` построен на Next.js, Python backend — на FastAPI. Браузер обращается к `/api/...` того же сервера Next.js; сервер перенаправляет запросы на локальный Python API. Аналитические формулы остаются в pandas/NetworkX: CLI и API вызывают один `run_analysis` с контрактом `AnalysisResult`. Суммы и количество операций сверяются между `edges.parquet` и `transactions.parquet` по каждой направленной паре; некорректные входные данные останавливают расчёт.

Python API хранит рассчитанный результат в памяти и обновляет его при изменении данных или конфигурации. После изменения Python-кода перезапустите backend, чтобы загрузить новые функции. Поиск и фильтры работают с готовым результатом. HTTP-выгрузки формируются из текущего расчёта; сохранённые CLI-файлы в `outputs/` не используются как источник для браузера. Идентификаторы в JSON передаются строками.

Признаки описывают число плательщиков/получателей, наблюдаемые потоки, схождение цепочек от seed, посредничество и межкластерные связи. Louvain выделяет сообщества на неориентированной проекции с суммой потоков в обе стороны; расчёт потоков и основной граф остаются направленными.

Роли: `consolidator`, `distributor`, `transit`, `terminal`, `coordinator`, `peripheral`. Роль — гипотеза о наблюдаемой структуре. `role_score` показывает силу её признаков и не является вероятностью правонарушения. Необязательно, чтобы все шесть ролей встречались в конкретной выборке.

Стартовые пороги текущей конфигурации:

| Роль-кандидат | Условия допуска |
|---|---|
| `consolidator` | ≥ 3 плательщиков и достижимость от ≥ 2 разных seed; граница не даёт усиления за удержание |
| `distributor` | ≥ 10 получателей и `out_deg / max(in_deg, 1) ≥ 2` |
| `transit` | Положительные вход и выход, `0.8 ≤ out_kzt / in_kzt ≤ 1.2`; исключены seed и глубина 4 |
| `terminal` | Положительный вход, нет исходящих связей; исключены seed и глубина 4 |
| `coordinator` | Положительная betweenness ≥ Q90 положительных значений, ≥ 2 соседних сообществ, достижимость от ≥ 2 seed |
| `peripheral` | Базовая гипотеза при отсутствии более сильных допустимых кандидатов |

Основная роль имеет максимальный допустимый скор. Равенства разрешаются в порядке `coordinator → consolidator → distributor → transit → terminal → peripheral`. Полные формулы `role_score`, альтернативная роль и применимость усилений описаны в [методологии](docs/METHODOLOGY.md). Betweenness оценивается по 256 исходным узлам с `random_seed=42`, без денежных весов расстояния.

Приоритет складывается из нормализованных признаков:

```text
priority_score = 0.35 × схождение seed-цепочек
               + 0.25 × max(входящий, исходящий объём)
               + 0.25 × betweenness
               + 0.15 × число плательщиков
```

Нормализация каждого признака: `min(x / Q95(x > 0), 1)`. При отсутствии положительных значений результат равен нулю. Шкалы сохраняются с результатами. Приоритет не умножается на `role_score` и не штрафует автоматически границу наблюдения. Точные правила, пороги и порядок выбора роли описаны в [методологии](docs/METHODOLOGY.md); схема компонентов — в [архитектуре](docs/architecture.md).

Временной бонус сопоставляет входы с выходами через 1–2 календарных дня по FIFO, расходуя каждую сумму только один раз. Переводы одного дня исключены из сопоставления: их порядок неизвестен. Карточка показывает дневные потоки, совместимый объём и его долю от меньшего из входа/выхода. Этот признак усиливает допустимую гипотезу транзита, но не входит в формулу приоритета.

Дополнительный слой событий выявляет всплески относительно других активных дней, групповые поступления, повтор состава плательщиков, последующий выход по FIFO, повторяющиеся маршруты A→B→C и циклы длины 2–4. Параметры находятся в `config.json` → `patterns`. Он не меняет формулы ролей и приоритета. Каждое событие содержит проверяемые ссылки на строки выгрузки; одинаковые строки сохраняются как отдельные наблюдения.

Для циклов отдельно указаны строгая последовательность дат, неизвестный порядок операций одного дня, структурное замыкание без совместимого эпизода и незавершённая проверка. Если поиск достигает лимита, приложение сообщает о неполноте. Отсутствие события не означает отсутствие деятельности. Суммы шагов маршрутов и разных событий не складываются в объём прослеженных средств.

HTML-справка показывает до восьми событий и трёх эпизодов каждого, явно отмечая сокращение. JSON включает весь набор. Справка формируется из расчёта без LLM; детализация, граф и скачивание проверяют версию данных, чтобы не смешивать разные расчёты.

## Проверка качества

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Тесты проверяют расхождения агрегатов и транзакций, неизвестные концы рёбер, обязательные поля, сохранение соседних `int64`-идентификаторов выше `2^53`, изолированные узлы, ограничения для seed и четвёртого колена, диапазоны и схемы выгрузок, FIFO без двойного зачёта, повторяемость и независимость приоритета от силы роли. Повторяемость проверяется также двумя полными расчётами исходного набора с приближённой betweenness.

Тесты HTML-графа проверяют строковые `gid`, направления, отсутствие внешних JS/CSS-ресурсов и сохранение выбранного клиента при ограничении числа узлов. Для проверки TypeScript и сборки интерфейса:

```powershell
npm run build --prefix frontend
```

Фактический вид, поиск, переход к клиенту и взаимодействие с графом проверяются отдельно в браузере. Готовность Python API доступна по [http://127.0.0.1:8000/api/health](http://127.0.0.1:8000/api/health); ответ `200` означает, что анализ данных выполнен успешно.

Правильных ролей в данных нет, поэтому accuracy/F1 не рассчитываются. Проверка ролей включает числовое обоснование, крайние случаи и ручной разбор представителей. Одинаковые данные и конфигурация должны воспроизводить роли, сообщества и ранжирование; длительность и время запуска закономерно меняются.

Проверенный запуск с новым слоем событий на предоставленном наборе 23.09.2026: **2,64 с** от начала CLI-расчёта до готовых выгрузок, включая загрузку аналитических зависимостей. Это измерение на рабочей машине, а не гарантия для любого оборудования. Фактические значения каждого запуска записываются в `run_metadata.json` (`cold_end_to_end_seconds` и `total_seconds`). Лимит хакатона — пять минут; сравнивать с ним нужно полный CLI-расчёт, а не переключение фильтра уже открытого интерфейса.

Найдено 974 события с участием 1 177 клиентов: 133 всплеска, 66 групповых поступлений, 5 повторов состава, 297 последующих выходов, 86 повторяющихся маршрутов и 387 циклов. Из циклов 98 имеют строго последовательный эпизод, 37 требуют уточнения порядка внутри дня, 252 являются только структурными замыканиями. Поиск заданной области завершён полностью. Это результаты правил, не число нарушений.

Получено 88 сообществ и 20 строк топа. Распределение ролей: `consolidator` — 128, `coordinator` — 17, `distributor` — 56, `peripheral` — 937, `terminal` — 1 050, `transit` — 60. В исходном графе 35 слабосвязных компонент: 16 с рёбрами и 19 изолятов. Это результат текущей конфигурации, а не известная разметка. Проверенные примеры приведены в [демо](docs/DEMO.md).

Выход превышает вход у 377 клиентов: у 354 наблюдается положительный вход, ещё у 23 входящих переводов в выборке нет. Эти случаи показывают неполноту наблюдения и не являются самостоятельным доказательством нарушения.

## Ограничения интерпретации

- Узел на глубине 4 может не иметь исходящих рёбер из-за остановки обхода. Он не получает `terminal` или `transit` по простому правилу потоков; утверждать удержание средств на этой границе нельзя.
- У seed-клиентов не видна полная входящая часть сети. Для них также исключены простые правила `terminal`/`transit`.
- Исходящая сумма выше входящей совместима с неизвестным начальным остатком и неполной выборкой. Это не доказательство нарушения.
- Граф ограничен одним банком, одним месяцем и порогом суммы. Отсутствие перевода в выборке не доказывает его отсутствия в действительности.
- Структурное сообщество не является доказанной организацией. `coordinator` обозначает гипотезу о связующем положении, а не доказанное управление другими клиентами.
- Маршрут в графе и близость дат не доказывают движение одних и тех же денег. В данных нет точного внутридневного порядка операций.
- `peripheral` включает случаи недостатка наблюдаемых признаков и не означает, что клиента можно считать безопасным.

## Рост до миллиона узлов

Текущий NetworkX-пайплайн рассчитан на небольшой хакатонный набор; запуск на миллионе узлов без изменения вычислительного слоя не заявляется. При росте данные нужно агрегировать пакетно в колоночном движке, графовые вычисления перенести в эффективный движок, betweenness оценивать по выборке источников. Интерфейс должен получать только выбранные подграфы и агрегаты сообществ. Фоновые задания, хранилище результатов и API добавляются по частоте обновлений и числу пользователей. Формулы ролей, форматы результатов и объяснения сохраняются как независимый слой.
